# Blog Markdown rendering and navigation

## Symptoms

Blog links using canonical `/documentation/<locale>/...` paths fall through the development
server to the Angular application. Without converting the entry to a hash route, initial
navigation returns to the homepage. A table of contents can also disappear after rendering.

## Verified rules

Resolve application links against the current origin, retain the documentation locale,
query and section fragment, and use Angular's Location service to produce hash-mode URLs.
Delegate unmodified primary clicks to the router; keep external links and modified clicks
native. Normalize canonical documentation entry paths before Angular bootstrap. Production
static documentation continues to use its readable canonical paths.

In ngx-markdown 21, `ready` fires before the source `load` event. Build heading IDs, the
table of contents and code toolbars on `ready`; updating reading time on `load` must not
clear those headings. Wrapping code must be idempotent and copying must preserve the code's
original whitespace.

API pages are generated by Dokka and merged into `dist/site/api`, independently of the
Angular development server. Use explicit `/api/<module>/index.html` navigation targets.
Do not mistake an HTTP 200 from the development SPA fallback for a working API page.

## Verification

The real Markdown component regression loads an HTTP source, preserves the rendered table
of contents, follows a Chinese documentation link through the router and copies the original
Kotlin code. The policy suite checks all six localized blog articles and every API navigation
target against the merged eight-module deployment fixture. Production generation verifies
all 150 static documentation pages and links. Browser verification opens the KEFS guide from
the KMP article and displays the shared compatibility table.
